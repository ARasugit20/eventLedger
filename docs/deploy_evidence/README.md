## Hosted concurrency result

Generated by [`scripts/hosted_concurrency_test.py`](../../scripts/hosted_concurrency_test.py):

```bash
python3 scripts/hosted_concurrency_test.py \
  --base-url https://eventledger-production.up.railway.app
```

Measured on **2026-09-07** against Railway region `iad`:

- 50 concurrent `POST /events` with one shared `idempotency_key`
- **1 × 201**, **49 × 200**, **0 × 5xx**
- **1** unique event UUID across all 50 responses
- **109.71 requests/second** for the 50-request burst (0.456 s wall clock)

### Why lifecycle fields differ across responses

The 50 responses agree exactly on identity (`id`, `idempotency_key`,
`event_type`, `payload`) but not on `status`. Observed statuses were
`received` and `processed`, because the worker claims and processes the
event while duplicate responses are still being served. That is expected
at-least-once behavior, not a dedupe failure — only one row exists.

## Measurement boundary

The 109.71 rps figure is a **50-request burst over the public internet from a
laptop**, not a sustained throughput benchmark. It is not comparable to the
local container benchmark in [`loadtest/results.md`](../../loadtest/results.md),
which used Colima with different concurrency, duration, and network path.
No sustained hosted throughput has been measured.
